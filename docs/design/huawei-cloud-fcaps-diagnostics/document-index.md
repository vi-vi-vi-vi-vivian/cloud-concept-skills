采用已确认的方案二。FCAPS 仍为主地图，文档按条件进入；命令定义不复制到文档目录。

| 文件 | 职责 |
| --- | --- |
| references/documents/index.md | 何时查文档、怎样核对来源、不可访问时怎样处理 |
| references/documents/huaweicloud.md | 条件路由，按 F/C/A/P/S 关联官方文档和现有契约 |
| references/documents/catalog.jsonl | 归档与补充来源合并后的最小元数据 |
| QA documents.py | 根据本地归档生成索引并检查一致性；不联网或执行原文 |
| QA documents-links.json | 已人工核验的补充链接、标题、栏目及核验日期 |
| QA documents-source.json | 来源日期、清单散列、逐篇正文散列、索引散列；不进入技能载荷 |

每行元数据只有 id、title、section、url。id 从官方路径去除 .md／.html 后缀生成，保留站点与语言路径，不随标题修改；同页两种格式只登记一次。归档保留已有 Markdown 地址，新增来源保留实际核验的 HTML 地址。section 采用服务与官方栏目，未自动猜测全部页面的 FCAPS 类别。

已知命令直接读原契约。需要解释、遇到环境差异或缺少依据时进入文档分支；精选路由未覆盖的主题再搜索 JSONL，只读取命中行。归档正文、图片和读取缓存继续留在技能之外；运行指引不依赖作者机器的绝对路径。

## 生成与更新

1. 使用已有两个 llms manifest 和对应 Markdown。声明实际快照日期，不用构建日期冒充上游更新时间。
2. 读取每篇首个 H1 作为标题。代码输出中的后续 H1 不当标题；官方域名、栏目路径与归档内路径均检查。
3. 补充来源先按官网标题与正文核验，登记 documents-links.json。build 合并两类元数据，并分别同步归档日期与补充核验日期。--report 输出归档正文变化的文档 ID；补充链接的元数据散列另存回执，不冒充原文正文散列。
4. 根据变化 ID 查精选主题和来源记录，复核受影响契约。正文更新不自动改写命令或验证状态。
5. check 对比清单、归档正文散列、补充元数据和精选引用。重复 ID/URL、同页重复格式、未知来源、正文混入、内容漂移及入口日期不同步均失败。

此流程核验声明来源的一致性，不证明所有地址当前在线可用。Markdown／HTML 的读取与正文有效性规则只在运行入口定义。2026-10-22 直接请求 HSS 两种地址均返回 HTTP 200 安全验证页；网页读取工具取得了实际正文。因此 HTTP 状态不能作为正文通过条件。原文是参考资料，修复步骤不自动成为执行授权。
